## Purpose and non-negotiable scope

This data-backed proposal was approved on `2026-07-14` and applied to the
live BtS building XML. The implementation changes only `<iCost>` and the
direct output fields recorded in the companion manifest. It does **not**
change Python, DLL behavior, recipes, prerequisites, category limits,
corporation thresholds, AI wiring, or mechanics.

Live sources reviewed:

- `CoreFiles/Sid Meier's Civilization IV Beyond the Sword/Beyond the Sword/Assets/Python/Screens/CvIndustryFlowData.py:11-96` defines the processing and composite chains, and `:98-239` maps corporation families and their minimum three active composites.
- `CoreFiles/Sid Meier's Civilization IV Beyond the Sword/Beyond the Sword/Assets/Python/Screens/CvIndustryAdvisor.py:11-42` keeps the 11 core entries and consumes the flow data for processor/composite display.
- `CoreFiles/Sid Meier's Civilization IV Beyond the Sword/Beyond the Sword/Assets/XML/Buildings/CIV4BuildingInfos.xml:39285+` is the live cost/output source; the companion manifest fingerprints every non-cost/non-output XML field.
- `third_party/beyond-the-sword-sdk/CvGameCoreDLL/CvCity.cpp` enforces local/connected bonus gates and industry limits; `CvPlayerAI.cpp` consumes those gates in AI evaluation.
- `docs/archive/plans/CIVIC_INDUSTRY_OVERHAUL_IMPLEMENTATION_PLAN.md:33-55, 70-159` is useful historical context for the category/cap and supply-chain intent, but live XML/Python/DLL remain authoritative.

### Design principles

1. Preserve the current flow: raw resource -> processor -> synthetic good -> composite -> corporation is already the right structure.
2. Buff the buildings, not the gates: retain recipes, local/connected resource checks, category slots, corporation founding thresholds, and AI inputs exactly as live.
3. Make food buildings visibly food buildings: every food-oriented row gains **+2 literal Food** through `YieldChanges/Food`; Millers' Guild also gains retention.
4. Prefer output buffs over discounts: only seven high-cost late-game entries receive a limited cost reduction; no cost increases and no output reductions are proposed.
5. Keep every value XML-native: only existing `iCost`, scalar output, `YieldChanges`, `YieldModifiers`, `CommerceChanges`, and `CommerceModifiers` fields are used.

### Inventory note

The requested review grouping is **11 CORE / 19 LUXURY / 39 COMPOSITE = 69**,
while the live mechanical categories are **11 CORE / 20 LUXURY / 38
COMPOSITE**. The difference is
`BUILDING_INDUSTRY_SCULPTORS_YARD`: it is mechanically a `LUXURY` processor
that produces Marble Statuary. The requested table partition places that one
processor in the 39-row `COMPOSITE` *review bucket only*; the table and JSON
retain its live category and propose no category or recipe change.

### Category targets

| Review category | Rows | Target |
| --- | ---: | --- |
| CORE | 11 | Increase the direct payoff of each local improvement specialization; farm/pasture offices become +3 Food. |
| LUXURY | 19 | Increase the processor's local reward without changing synthetic-good production or its resource gate. |
| COMPOSITE | 39 | Raise the reward for connected two-/three-good commitments, generally +1 GPP plus a matching output; provision composites gain +2 Food. |

### Output-field legend

`Y` = `YieldChanges` (Food/Production/Commerce); `YM` = `YieldModifiers` (Food/Production/Commerce); `C` = `CommerceChanges` (Gold/Research/Culture/Espionage); `CM` = `CommerceModifiers` in that order. `FK`=Food Kept; `H`=local/area/global health; `Hap`=local/area/global/state-religion happiness; `GPP`=flat/rate; `Maint`, `Worker`, `Mil`, `Space` are modifiers; `TR`=local/coastal/global routes; `TR%`=trade/foreign-trade modifiers; `XP` and `Power` are direct scalar outputs. Every listed value is exact; fields not in this schema are protected by the row fingerprint and are not proposal targets.
